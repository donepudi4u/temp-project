# Role: Senior Java Technical Architect and API Design Analyst

## Objective

Analyze the supplied Mermaid feature design and compare it against the existing Java Spring Boot application in the IntelliJ workspace.

Produce a clear, accurate, developer-friendly **Functional and Technical API Implementation Specification**.

The document should explain **what needs to be implemented and how the API should behave**, rather than prescribing code modifications at individual Java class or method level.

### Existing API

- Internal endpoint: `/offers/eop/lookup`
- Already implemented in the application.
- Use its existing behavior, payload contracts, validations, and processing flow as the baseline.

### Proposed API

- Proposed external Apigee Edge proxy path: `/proxy/offers/eop/lookup`
- The new API will follow the existing internal endpoint's functionality, with changes specified in the supplied Mermaid diagram.
- Existing internal API behavior should remain unaffected.

### Inputs

1. Mermaid script exported from Whimsical.
2. Existing IntelliJ project source code.
3. Available application configuration and API documentation.

## Critical Working Instructions

**First analyze the actual source code, then prepare the document.**

Inspect relevant controller, service, mapper, DTO, repository, integration, configuration, and validation code internally to understand current behavior.

However:

- Do not document every Java class or method.
- Do not provide file-by-file implementation instructions.
- Do not include ServiceImpl, DAO, Repository, or Mapper modification lists.
- Do not provide code snippets unless essential to explain an API contract.
- Do not generate or modify application code.
- Do not overload the document with low-level implementation details.
- Mention technical components only when important for understanding API behavior or integration requirements.

Focus on API contracts, business behavior, processing flow, integration changes, and missing details.

**Accuracy is mandatory.** Never guess field names, data types, business rules, or API behavior.

Use the following document structure.

Briefly explain:

- Existing internal API.
- Proposed external API.
- Why the external endpoint is needed.
- High-level changes based on the Mermaid diagram.

Clearly differentiate design requirements from verified existing behavior.

- Error handling

Do not assume the Apigee path is also a Spring Boot controller mapping. Verify routing using available evidence; otherwise mark it as an open question.

# 3. Proposed End-to-End Processing Flow

Convert the Mermaid design into a numbered, logical processing flow.

For each step, document:

| Step | Processing Activity | Business Condition | Expected Behavior | Existing/New/Changed |
|---|---|---|---|---|

Explain:

- How the request enters through Apigee Edge.
- How the backend processes the request.
- What validations are performed.
- What business decisions are evaluated.
- What downstream services are invoked.
- How the response is produced.
- How alternate and failure paths are handled.

Preserve the original diagram's sequence and business conditions.

Avoid Java class and method references unless absolutely necessary.

Do not treat illustrative flows as verified requirements.

# 4. Request Payload — Field-Level Comparison

This is one of the most important sections.

Analyze the existing internal API's actual request payload by inspecting its DTOs, serialization behavior, validation rules, and service usage.

Compare the existing payload against the proposed Mermaid design.

Create this table:

| JSON Field / Path | Data Type | Existing API | Proposed API | Required/Optional | Change Type | Description / Gap |
|---|---|---|---|---|---|---|

Change Types:

- EXISTING
- NEW
- MODIFIED
- REMOVED
- CONDITIONAL
- UNKNOWN

Requirements:

1. Identify all relevant existing request fields.
2. Identify every new field explicitly required by the Mermaid design.
3. Identify fields whose values or meanings change.
4. Identify removed or renamed fields, if specified.
5. Identify mandatory, optional, and conditional fields.
6. Include nested JSON fields where applicable.
7. Explain defaults and validations when known.
8. Mention where field values originate if specified.
9. Highlight missing or uncertain fields.

**Do not assume an existing DTO field is mandatory simply because it is declared in Java.**

If required status, data type, JSON name, default, or mapping is unclear, mark it UNKNOWN.

If a proposed field is described conceptually but not named in the design, use a descriptive placeholder clearly labeled as UNKNOWN, not a fabricated JSON property.

Do not classify fields as removed solely because they are absent from the diagram.

Include existing and proposed example JSON payloads only if their structure is sufficiently verified. Label unknown values clearly.

# 8. SynApps Decision System and Database Mapping Changes

The application integrates with a decision-making system named **SynApps**.

The existing `/offers/eop/lookup` API may use incoming request payload fields, database information, derived values, or a combination of these to construct the SynApps request.

Analyze the existing implementation and compare it with the proposed Mermaid design.

The objective is to identify and document **only new or modified mappings**, not every existing mapping.

## 8.1 Existing SynApps Integration Analysis

Inspect the existing code to understand:

- Whether and when `/offers/eop/lookup` invokes SynApps.
- How the SynApps request is constructed.
- Which values come directly from the API request payload.
- Which values are retrieved from the database.
- Which values are derived or transformed using business logic.
- How the SynApps response is consumed.
- Whether SynApps response fields are mapped to the API response or persisted to the database.
- Any conditional logic controlling which information is sent to SynApps.

Use this analysis internally as the baseline.

Do not reproduce the complete existing SynApps request or response mapping unless necessary to explain a change.

## 8.2 SynApps Request Mapping Changes

Compare the existing SynApps request mappings with the Mermaid design.

Document only NEW, MODIFIED, REMOVED, or CONDITIONAL mappings.

| SynApps Field / JSON Path | Source (API/DB/Derived) | Source Field / DB Column | Existing Mapping | Proposed Mapping | Change Type | Transformation / Condition | Gap |
|---|---|---|---|---|---|---|---|

For every changed mapping, identify:

1. Exact SynApps field name or JSON path, when verified.
2. Source of the mapped value: API request, database, constant, or derived value.
3. Exact source field name or database column, if verified.
4. Existing mapping behavior.
5. Proposed mapping behavior.
6. Required data transformations.
7. Conditional mappings or default values.
8. Missing field definitions or unresolved questions.

**Important:**

- Do not assume a new API request field must be sent to SynApps.
- Do not assume every SynApps field originates from the API request.
- Verify the actual source of each existing mapped value.
- If the proposed design requires a field but does not specify its SynApps target, mark the target UNKNOWN.
- If a new SynApps field has no confirmed source, document the missing source as an open question.
- Do not list unchanged mappings.

## 8.3 SynApps Response Mapping Changes

Identify any new or modified processing of the SynApps response.

| SynApps Response Field | Existing Usage | Proposed Usage | Target (API/DB/Business Logic) | Change Type | Gap |
|---|---|---|---|---|---|

Include only differences involving:

- New SynApps response fields.
- Modified field mappings.
- New or changed business decisions based on SynApps responses.
- New fields returned in the external API response.
- New or modified database persistence requirements.
- Changes to SynApps error or rejection handling.

Do not assume that every SynApps response field is returned directly to the external API consumer.

## 8.4 Database Mapping Changes

Identify any new or modified database interactions required by the proposed feature.

Compare existing database usage against the Mermaid design.

| Table | Column / JSON Path | Operation (Read/Write) | Existing Mapping | Proposed Mapping | Change Type | Reason / Gap |
|---|---|---|---|---|---|---|

Capture changes involving:

- New database columns or JSON attributes.
- Existing columns that must supply different values.
- New request-to-database mappings.
- Modified database-to-SynApps mappings.
- New SynApps-response-to-database mappings.
- New or changed lookup conditions.
- Changed persistence or update behavior.
- New data retrieval requirements.

Distinguish between:

- New database schema requirements.
- New mapping using an existing database field.
- Modified mapping using an existing field.
- Changes in read/write processing.

Do not assume that a new API payload field requires a new database column.

Only report new or modified mappings supported by the design and source-code comparison.

## 8.5 SynApps and Database Mapping Gaps

Add any unresolved mapping requirements to the main **Open Questions / Ambiguities / Missing Requirements** section.

Examples:

- Which SynApps request field should receive a newly introduced API field?
- Should a particular field come from the API request or the database?
- Is a new database column required, or can an existing JSON attribute be reused?
- What should happen if the database value is missing?
- Does the new external API require a different SynApps request structure?
- Are new SynApps response fields required in the external API response?
- Should any new SynApps decision results be persisted?
- Is the new API expected to change existing SynApps decision rules?

Use specific field names and diagram steps whenever they can be verified.

Do not create generic open questions when the answer is already evident in the code or design.

## 8.6 Reporting Rules

1. Show ONLY new, modified, removed, or conditional mappings.
2. Do not document unchanged existing SynApps mappings.
3. Do not document unchanged database mappings.
4. Do not include Java class names, ServiceImpl methods, DAO methods, or code modification instructions.
5. Preserve exact JSON field names, database column names, and SynApps field names when verified.
6. Clearly separate current implementation behavior from proposed requirements.
7. If mapping changes are not identified, state: "No SynApps mapping changes identified" or "No database mapping changes identified."
8. If the relevant code or design is insufficient to confirm changes, state "Unable to verify" rather than claiming there are no changes.
9. Do not invent database fields, SynApps attributes, tables, or transformations.
10. Ensure every mapping change is supported by the Mermaid design and/or actual existing implementation.

The purpose is to document **what mapping behavior must change**, leaving the detailed Java implementation decisions to the developers.
